# AGENTS.md

This file provides guidance to coding agents (Claude Code and others) when working with code in this repository. `CLAUDE.md` is a symlink to it.

## What this is

LumeEngine is an FFmpeg 9-based media player engine for Apple platforms (iOS 18+, tvOS 18+, macOS 15+, visionOS 2+), built as a Swift 6 package for the Lume IPTV app. It is an original architecture designed around a stability doctrine: **PLAN.md is the authoritative design document** — §3 catalogs legacy-engine failure modes and the structural countermeasures that are hard requirements, §4 covers architecture decisions (D1–D9), §9 the roadmap. When making design decisions, check PLAN.md first.

## Relationship to Lume (`../Lume`)

The consumer app lives in the sibling repo `../Lume`. Most bug reports and feature requests arrive in Lume terms (channels, EPG, IPTV providers, engine fallback) — when triaging one, first decide whether it belongs in the engine or in the app, and read the relevant Lume code before changing engine behavior.

- Lume ships four engines behind an engine-priority fallback chain: LumeEngine (beta), KSPlayer, VLC, and AVPlayer. The LumeEngine integration code lives in `../Lume/Lume/Views/Player/` (`LumeEngineEngineView.swift`, `LumeEngineCoordinator.swift`, `LumeEngineControlsOverlay.swift`) — engine-side fixes go here, app-side wiring there.
- The consumer contract LumeEngine must satisfy (PLAN.md §2.1) is defined by `../Lume/Lume/Views/Player/` (`TVPlaybackEngine.swift`, `PlaybackClock.swift`, `PlaybackRetryController.swift`, the other `*EngineView.swift` implementations) and `../Lume/Lume/Services/Player/PlayableMedia.swift`.
- Division of responsibility: the engine reports typed errors/events and never retries on its own schedule — reconnect/backoff policy, engine fallback, and UI overlays are Lume's job.
- Lume has its own `AGENTS.md` (with a `CLAUDE.md` symlink); consult it when working on that side.
- Lume references this repo as a **local** SPM package at `../LumeEngine`, so uncommitted engine changes build straight into the app — and a Lume clone without a LumeEngine sibling (plus its FFmpeg xcframework) will not resolve. Both repos' contributor docs say so; keep them in sync.

## How FFmpeg reaches the build

`Package.swift` resolves the `CFFmpeg` binary target two ways, and the conditional is deliberate — don't "simplify" it away:

- `BinaryDependencies/FFmpeg.xcframework` exists → local `path:` binary target. This is the development override, so anyone iterating on `build/` tests their own FFmpeg.
- Otherwise → `binaryTarget(url:checksum:)` against the artifact attached to a GitHub release. Consumers (and a plain `git clone && swift build`) take this path and need nothing from `build/`.

dav1d (software AV1, BSD-2-Clause) is part of that build: `build/scripts/build-dav1d.sh` cross-compiles it with meson for each slice, `build-ffmpeg.sh` calls it and links it via `--enable-libdav1d`, and `libdav1d.a` is merged into `libffmpeg.a`. Its version counts as the FFmpeg build's for everything below.

The artifact URL is versioned by the FFmpeg build it contains, not by the engine release it hangs off: bump it only when `build/versions.json`, the configure flags, or the patch set change — and then in the same change as the pipeline edit, or consumers link a binary that doesn't match the source.

Since the checksum can only exist once a release has built the artifact, a release that changes the FFmpeg build ships in two steps under one version: push the tag, let the release job attach the xcframework, point `Package.swift` at that URL and checksum (verified with `swift package compute-checksum` on the downloaded zip, and a fresh clone without `BinaryDependencies/`), merge, then move the tag onto that commit. Re-pushing the tag runs the release job again, and it skips itself when the release already carries `FFmpeg.xcframework.zip` — a rebuild is not bit-identical, and replacing a published zip would break the pinned checksum for everyone. Don't remove that guard. (Up to v0.2.x, the pointer bump went out as the next patch release instead, e.g. #36 → v0.2.1.)

## Licensing (public repo)

Engine source is **MIT** (`LICENSE`). FFmpeg is linked under the **LGPL 2.1+**, and anything added under `build/patches/` modifies FFmpeg source and is therefore LGPL, not MIT. `THIRD-PARTY-NOTICES.md` is the single source of truth for what is linked and what downstream apps must do; update it in the same change whenever you touch `build/versions.json`, the configure flags in `build/scripts/build-ffmpeg.sh`, or the patch set. Two claims there are load-bearing and must stay true: the build is LGPL (`--disable-gpl --disable-nonfree`, no GPL external libs), and the `LumeEngine` product stays **dynamic** so FFmpeg remains relinkable.

## Commands

```bash
swift build
swift test                                    # full suite
swift test --filter TimestampUnwrapperTests   # one suite
swift test --filter DecoderTests/testName     # one test
swift run LumeEngineDemo                      # macOS demo app with diagnostics HUD
swift run lumectl probe <url>                 # tracks, codecs, live/seekable, HDR tags
swift run lumectl play <url> --duration 60    # headless run: events, heartbeat, startup, exit status
```

`lumectl` reproduces a provider issue without the app: it drives a `PlayerSession` headlessly (muted) and prints what the engine reports — typed events, the `Diagnostics` heartbeat with the delivery rate, the `StartupTimeline`, `lastStallReason` on every stall, the `EngineError` (with its HTTP class) on failure. Exit status: 0 ok, 3 open failed, 4 playback failed, 5 stalled. URLs are redacted to scheme and host unless `--show-urls`, since IPTV URLs carry credentials — keep it that way. Its logic lives in `Sources/LumeCtlCore` (tested from `LumeCtlTests.swift`); `lumectl --help` lists the options. When a Lume report arrives, a `lumectl play` run against the same URL (with `--json` or `--record-events run.jsonl`) is usually the quickest way to tell an engine problem from a provider one.

Prerequisites:
- `BinaryDependencies/FFmpeg.xcframework` must exist before anything compiles. Build it once (or after bumping `build/versions.json`):
  ```bash
  brew install meson ninja nasm                # dav1d's build; nasm only for x86_64 slices
  build/scripts/fetch-sources.sh               # FFmpeg + dav1d tarballs, SHA-256 verified
  build/scripts/build-ffmpeg.sh macos-arm64    # one slice is enough for local dev
  build/scripts/make-xcframework.sh
  ```
- Tests need a host `ffmpeg` CLI (Homebrew) — fixtures are generated lazily on first test run by `Tests/LumeEngineCoreTests/Fixtures/generate-fixtures.sh` into `TestStreams/generated/` (gitignored, idempotent). `Fixtures.swift` finds Homebrew ffmpeg automatically; override with the `FFMPEG` env var. The closed-caption and bitmap-subtitle fixtures (`captions.ts`, `pgs.mkv`, `dvbsub.ts`, `dvdsub.mkv`) also need `python3` (the one Xcode's command-line tools provide is enough), because no ffmpeg CLI option writes captions into the video or renders subtitle bitmaps; without it those fixtures are skipped and their tests fail as missing.

CI (`.github/workflows/ci.yml`) builds the macOS FFmpeg slice (cached on `build/versions.json` + scripts + patches hashes) and runs `swift test` with a strict one-thread cooperative pool (see above), checks the Markdown docs offline (`.github/scripts/check-docs.py`: relative links and in-repo anchors resolve, `CLAUDE.md` is still the `AGENTS.md` symlink — run it after editing docs), then cross-compiles the library for iOS and tvOS via `xcodebuild` (compile-only, one cached slice each — visionOS is left to local verification because that matrix entry was never confirmed on a runner — the xrOS SDK ships with Xcode, but a visionOS *destination* also needs Xcode's visionOS platform component); tagged releases build all 10 platform slices and attach the xcframework.

## Architecture

Three-layer target structure (`Package.swift`):

- **`CFFmpeg`** — binary target wrapping `BinaryDependencies/FFmpeg.xcframework` (FFmpeg 9.0.x static libs, LGPL config, built by `build/scripts/`).
- **`Sources/LumeEngineCore`** — the engine, no UI. Uses `internal import CFFmpeg` + library evolution so FFmpeg types never leak into consumers' compiles (apps can link other FFmpeg-based engines without symbol/module collisions — this is why the product is a **dynamic** library; don't change that). This is not theoretical: removing `-enable-library-evolution` broke Lume immediately, because it links FFmpegKit too and Clang then sees `enum AVPixelFormat` defined differently in `CFFmpeg` and `Libavutil`. Nesting the headers under `lume_ffmpeg/` stops header-path collisions but not C-namespace redefinition — evolution is what keeps `CFFmpeg` out of the consumer's compile.
- **The evolution flag is conditional in `Package.swift`** (`isVersionedDependency`, detected by `/checkouts/` in `#filePath`), because SwiftPM forbids `unsafeFlags` in version-resolved dependencies and there is no safe library-evolution setting. Path dependencies — Lume, its worktrees via the `LumeEngine` symlink, and engine development — get the flag; `.package(url:from:)` consumers don't, and such a consumer must not link a second FFmpeg (tell them to vendor by path instead). Don't collapse either conditional in that manifest.
- **`Sources/LumeEngine`** — public facade: `LumePlayer` (`@MainActor @Observable`), `LumePlayerView` (SwiftUI).

### Control plane vs data plane (PLAN.md D1)

This split is the core invariant of the codebase:

- **Control plane = actors.** `PlayerSession` (actor, `Session/`) owns lifecycle, seek, track switching, and event emission. It never touches frames.
- **Data plane = dedicated threads.** Blocking FFmpeg calls (`av_read_frame`, `avcodec_receive_frame`) run on their own threads: `Demuxer` → `VideoDecoder`/`AudioDecoder`/`SubtitleDecoder` → `SystemRenderer`. Stages communicate only through `Concurrency/Channel` — a bounded, blocking, PTS-accounted channel that provides backpressure (producers park when full) and wakeable teardown. Never put a blocking FFmpeg call on an actor; never bypass channels between stages.
- **Actors and async code never block.** That includes waiting for a stage: every `shutdown(deadline:)` joins a thread, so the control plane hands joins to `Concurrency/DedicatedThread` and awaits them (session teardown) or doesn't wait at all (a retired track lane). The same goes for tests — a blocking `Channel.receive` belongs on a thread of its own (`Support/ChannelDrain.swift`, `DedicatedThread.run`), not in an `async` test body. CI enforces this by running the suite with `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` (a one-thread cooperative pool), where a blocking wait that only starved the pool before stalls or hangs the run instead; run `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 swift test` locally when touching concurrency.
- **The main thread is never on the data path.** UI state is a decoupled low-rate observation.

### Key invariants (from PLAN.md §3 — requirements, not style preferences)

- **Session epochs:** a `PlayerSession` opens exactly one URL; a new URL is a new session object. There is no rebuild-in-place, ever. Teardown joins data-plane threads before `avformat_close_input`.
- **Timestamp unwrapping at the demux boundary:** `Time/TimestampUnwrapper` normalizes all PTS/DTS to monotonic 64-bit engine time immediately after `av_read_frame` (handles MPEG-TS 33-bit wraparound), and `Time/TimelineFolder` folds the other discontinuities a live source produces (encoder restarts, catch-up chunks that restart PTS) out of the timeline. A seam is detected per continuous stream but corrected on all streams alike, so A/V sync across it stays what the source had; the folder resets on seek. Before folding, `Demux/ReplayFilter` drops what a reconnected source sends a second time (same stream, timestamp and size, arriving behind the newest timestamp) — folded first, a replay would play twice as a seam. Nothing downstream ever sees raw container time.
- **RAII FFI wrappers:** `FFI/Packet`, `FFI/Frame` etc. wrap `AVPacket*`/`AVFrame*` with deinit-based free. `@unchecked Sendable` is allowed **only** on these audited immutable-after-construction wrappers and on `Channel` — never on state-bearing types. No `Unmanaged` outside FFI.
- **A/V sync is Apple's job:** decoded frames are enqueued into `AVSampleBufferRenderSynchronizer` (`Render/SystemRenderer`). Do not add drop-frame heuristics or hand-rolled clocks.
- **The clock starts only once every lane has a frame at its renderer, and at the latest lane's first frame.** The buffer gate counts packets, so on its own it opens before a cold decoder (first VideoToolbox session after launch) has produced anything: audio plays over a frozen picture, then the late frames are shown as fast as they decode. A lane that joins later (live TS mid-GOP waiting for a keyframe) moves the start forward rather than leaving the picture empty. Only a lane that cannot buffer more or every lane at EOF lets the clock start without that.
- **Deinterlacing never costs the hardware decoder.** `Decode/VideoFilterGraph` (bwdif, falling back to yadif) sits between `avcodec_receive_frame` and delivery; VideoToolbox frames are downloaded with `av_hwframe_transfer_data` and filtered on the CPU. Do *not* "simplify" this into switching the codec to software when a stream is interlaced: that costs a mid-stream codec rebuild and keyframe resync at every interlaced/progressive splice, which live broadcasts (ad breaks in a 1080i match) are full of. Engagement is decided per frame from `AV_FRAME_FLAG_INTERLACED` (PLAN.md §3, failure 6) and, once engaged, everything stays on one path — `deint=interlaced` passes progressive frames through. Filter output carries the sink's time base, which a field-doubling filter *halves*; PTS and durations are rescaled back to engine µs in `VideoDecoder`.
- **Video decoders are chosen per path, never with `avcodec_find_decoder`.** `VideoDecoder.decoder(for:hardware:)` picks the decoder with a VideoToolbox config for the hardware path and a decoder that can run without hardware for the software path. For AV1 these are different decoders: FFmpeg's native `av1` is the only one with a VT hwaccel but returns `ENOSYS` without one, while `libdav1d` (registered first, so what `avcodec_find_decoder` returns) has no hardware path. The AV1 hardware path is only tried when `VTIsHardwareDecodeSupported` says the chip has it, since the native decoder has nothing to fall back to.
- **Tracks without a decoder are listed, never chosen.** `TrackInfo.isDecodable` asks the same lookups the lanes open with (`VideoDecoder.decoder(for:hardware:)` on both paths, `AudioDecoder`/`SubtitleDecoder.decoder(for:)`), and automatic selection passes over undecodable tracks (AC-4, MPEG-H in DVB/ATSC muxes) before language and default flag; only when nothing is decodable does it fall back to the old choice. Keeping such streams out of `avformat_find_stream_info` is not possible cleanly: its completeness check ignores `discard` (an AC-4 stream raises a TS probe from 5 s to 7 s of media, and pre-probe discard measured worse), so don't hack codecpar to get there.
- **HDR metadata is written on every delivered buffer, from the frame.** `Decode/HDRMetadata` turns the frame's mastering display (ST 2086) and content light level side data into Apple's big-endian SEI payloads on the pixel buffer in `VideoDecoder.deliver`, and HDR10+ (ST 2094-40) into a T.35 message the `SampleBufferBuilder` attaches per sample (`kCMSampleAttachmentKey_HDR10PlusPerFrameData`). No path keeps it by itself: VideoToolbox, as FFmpeg drives it, leaves its surfaces without either key, and the engine's own buffers carry only what it writes. Read the frame, not the codec parameters — FFmpeg already folds the container's boxes into every frame and lets the bitstream's SEI override them. Keys are written *or removed* on every buffer (pools recycle), and the format description is rebuilt whenever they change, because `CMVideoFormatDescriptionMatchesImageBuffer` compares them; don't replace that match with a cheaper key.
- **Multi-layer HEVC reaches the codec as its base layer only.** `Decode/HEVCBaseLayerFilter` drops every `nuh_layer_id > 0` NAL unit from packets and extradata before `avcodec_send_packet`/`avcodec_open2`. FFmpeg files an MV-HEVC stream's second-view SPS/PPS (DV profile 20, spatial video) alongside the base layer's, its VideoToolbox glue packs all of them into one `hvcC`, VideoToolbox rejects that session, and FFmpeg falls back to software *without an error* — 4K HEVC in software, which stutters on Apple TV. The engine presents only the base view, so stripping loses nothing. Relatedly, `VideoDecoder.isHardwareActive` is judged from the frames' pixel format, not from whether a VT device was attached, and such a silent fallback emits `.downgradedToSoftware` — keep it that way, or this class of bug goes invisible again.
- **Dolby Vision with an IPT base layer is converted, not tagged.** Profiles 5, 10.0 and 20 (compatibility ID 0) carry IPTPQc2, which shows pink/green as YCbCr. No colour attachment fixes that — the RPU reshaping changes per scene and Apple's decoders don't apply it to decoded frames — so `Decode/DolbyVisionConverter` turns each frame into HDR10 on the GPU in `VideoDecoder.deliver`, the one point every frame (hardware, software, deinterlaced) passes with its side data. Whether a frame is IPT is decided *per frame* by `Decode/DolbyVisionDetection`, never by the configuration record alone — remuxes mislabel HDR10 as P5 and broadcasts drop RPUs without changing it, and converting HDR10 as IPT gives wrong colours. Order: an `AVCOL_SPC_IPT_C2` frame is IPT; a frame with its *own* RPU is what the RPU's `signal_color_space` says (2 = IPT); a frame without one that states a matrix (BT.2020 PQ) is that matrix; only an untagged frame without its own RPU falls back to the record (genuine P5 often leaves the VUI matrix unspecified). "Own" matters because FFmpeg's HEVC decoder attaches the last RPU's `AV_FRAME_DATA_DOVI_METADATA` to every later frame; only `AV_FRAME_DATA_DOVI_RPU_BUFFER` marks the frame that carried one (AV1 attaches metadata only to its own frame). HDR10-compatible profiles (8.1 etc.) must stay on the zero-copy path. GPU refusals are per-frame (iOS refuses a backgrounded app); only a converter that can't exist gives up for the session.
- **Display criteria describe the output, not the container.** `PlayerSession.displayCriteria` (pure resolution in `Media/ContentDisplayCriteria`) is what an Apple TV with Match Content should switch the TV to: the refresh rate *after* deinterlacing (field rate turns 1080i50 into 50 Hz) and the dynamic range of what is presented (IPT Dolby Vision profiles are converted, so HDR10; every other Dolby Vision profile is presented as its base layer, so HDR10, HLG or SDR by its compatibility ID and the frames' transfer function). Never ask for Dolby Vision mode while the engine has no Dolby Vision output path — that belongs to the PLAN.md §7 compressed-`dvh1` spike. Before the first frame it is predicted from the stream; once the renderer has been handed frames, their colour tags and measured cadence (`Render/FrameCadence`) decide. Rates snap to the film/broadcast grid or ask for none — never an odd rate. Applying it is tvOS-only and opt-in (`Media/DisplayCriteriaMatcher`, or `LumePlayerView(…, matchesDisplayCriteria: true)`): one matcher per player screen, kept across sessions so zapping between same-mode channels never switches the TV, reset only when the screen goes away. The mode-switch blank is sat out with `PlayerSession.holdStart(for:)`, which the session bounds itself and the stall watchdog ignores — keep both, or a host that never releases wedges playback, or a held start reads as a stall.
- **Dolby Vision with an IPT base layer is converted, not tagged.** Profiles 5, 10.0 and 20 (compatibility ID 0) carry IPTPQc2, which shows pink/green as YCbCr. No colour attachment fixes that — the RPU reshaping changes per scene and Apple's decoders don't apply it to decoded frames — so `Decode/DolbyVisionConverter` turns each frame into HDR10 on the GPU in `VideoDecoder.deliver`, the one point every frame (hardware, software, deinterlaced) passes with its side data. Detection is the stream's DV configuration record *or* an `AVCOL_SPC_IPT_C2` frame; many P5 encodes leave the VUI matrix unspecified, so don't reduce it to the tag. HDR10-compatible profiles (8.1 etc.) must stay on the zero-copy path. GPU refusals are per-frame (iOS refuses a backgrounded app); only a converter that can't exist gives up for the session.
- **Audio is fitted to the negotiated route width, never the route's capability.** `AudioDecoder` reads `AudioOutputRoute.outputChannels` (the session's `outputNumberOfChannels`, followed through route-change notifications) per frame and remixes per `AudioLayoutPolicy` with an explicit `DownmixMatrix` — a fold-down mixes centre and surrounds in, it never drops channels. Don't switch it to `maximumOutputNumberOfChannels`: a renderer fed more channels than the session outputs failed outright on tvOS. The engine only observes the audio session; setting its category, activation or preferred channel count is the host's job (Lume does it). When the route narrows, `SystemRenderer` keeps audio decoded for the wider route out of the renderer.
- **How long a subtitle shows is the timeline's decision, not the decoder's.** Decoders hand `Subtitle/SubtitleStore` a `SubtitleEvent` (start, end *or none*, text, whether the track replaces the whole screen with each update); `Subtitle/SubtitleTimeline` decides the rest: an open cue ends at the next update of its track (capped at 16 s), an empty update on a closed-caption/DVB/PGS/DVD track is a clear that ends what is showing, a seek ends open cues, re-read ranges are deduplicated, and the store is bounded. Don't turn `end_display_time == UINT32_MAX` into a number in a decoder or drop empty updates there — both put stuck or stacked cues on screen.
- **Bitmap subtitles (DVB, PGS, DVD) are images on the cue, positioned by their own canvas.** `Subtitle/SubtitleBitmap` turns `SUBTITLE_BITMAP` rects into premultiplied sRGB `CGImage`s with a rect normalized to the canvas the decoder reports *after* decoding (DVB display definition, PGS presentation size, DVD `size:`), never to the video's pixel size — an HD DVB page over SD video, or PGS authored at 1080p over a 720p encode, would land off screen. The DVB context's size is zeroed before opening so the stream's display definition sets it. Bitmap cues carry empty `text` (text consumers like Lume show nothing rather than garbage); drawing them is the host's job, since `LumePlayerView` is bare video. The timeline bounds bitmap memory separately (`imageByteBudget`).
- **Closed captions leave the video lane through a tap, never a wait.** CEA-608 in A/53 side data (`AV_FRAME_DATA_A53_CC`) is lifted off each decoded frame in `VideoDecoder.receiveFrames` (before deinterlacing) by `Subtitle/ClosedCaptionTap`, stamped with the frame's PTS, and `trySend`-ed to an ordinary `SubtitleDecoder` running `ccaption` in real-time mode — a slow caption lane drops captions, never frames. The track is synthetic (`TrackInfo.embeddedClosedCaptionsIndex`) and appears in `PlayerSession.mediaInfo` once caption content is seen; `.opened` keeps the open-time track list, because no new `PlayerEvent` case may be added for it. Only CEA-608 field 1 (CC1/CC2) is decoded: FFmpeg has no CEA-708 (DTVCC) decoder, and teletext needs libzvbi, which the build does not include.
- **Zero global mutable state:** all configuration is `PlayerConfiguration` passed at session creation. No `static var` knobs.
- **No force unwraps / `as!` / `fatalError` in engine paths**; failures return typed `EngineError`. No `assertionFailure` in production channel/data paths — misuse degrades, never crashes.
- **Never scrape FFmpeg log strings for control flow** (`av_log` is diagnostics only). Silence is never a failure mode: pipelines are supervised, stalls are detected from playhead ground truth, and failures surface as typed `PlayerEvent`s on the session's `AsyncStream`.
- **Source URLs are credentials; nothing public carries one whole.** IPTV URLs hold the account (Xtream `/live/<user>/<pass>/…` paths, `token`/`password` queries, userinfo), FFmpeg names playlist, segment and key URLs in its warnings, and the bridged log is public so sysdiagnoses stay useful. Text bound for `os_log` or an `EngineError` message goes through `Errors/LogRedaction` (scheme, host, port and file extension survive; path, query and userinfo do not).
- Swift 6 strict concurrency (`swiftLanguageModes: [.v6]`) — keep it honest, don't suppress diagnostics.

### Tests

`Tests/LumeEngineCoreTests/` covers the historically crash-prone areas by design: timestamp wraparound (against a real wrap-seam fixture `wrap.ts`), channel backpressure/teardown, fixture-based decode, deinterlacing (against a field-coded `interlaced.ts`), Dolby Vision conversion (GPU output against an independent CPU reference; the real-stream cases use the non-redistributable samples in the gitignored `TestStreams/DolbyVision/` and skip without them, CI included), playback, and resilience via `Support/TortureHTTPServer.swift` (a fault-injecting local HTTP server — mid-stream errors, stalls, disconnects). New work in demux/decode/time/concurrency should come with tests here; add new media fixtures to `generate-fixtures.sh`, not as committed binaries.
